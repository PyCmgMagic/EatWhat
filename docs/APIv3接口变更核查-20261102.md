# APIv3 接口变更核查

核查日期：2026-11-02。对比本地 `EatWhat 业务服务 APIv2.openapi.json` 与 `EatWhat 业务服务 APIv3.openapi.json`。下文记录修复前的源码问题与接入建议；后续修复已完成，当前状态见 [APIv3 接入与验收](APIv3接入与验收-20261102.md)。核查及修复验证均未访问真实后端。

## 结论

- 版本从 `tencent-captcha-20261024` 更新为 `user-blocks-consent-20261026`。
- 两版均为 116 个路径、136 项 HTTP 操作，新增和删除操作均为 0，未发现请求参数、请求体或鉴权要求的业务变化。
- 主要变化是授权状态查询精简、登录响应 `loginId` 类型收窄，以及屏蔽能力的部署说明更新。
- 消除两种 OpenAPI 可空值及排他边界写法差异后，4 项操作存在响应契约变化：三个登录/注册操作及一个授权状态查询。

机器差异记录：[`../output/api-v3-diff-20261102.json`](../output/api-v3-diff-20261102.json)。复现：在仓库根目录执行 `node output/audit-api-v3.mjs`。脚本会展开本地引用、保留业务字段，归一化 OpenAPI 3.1/3.0 的可空值与边界写法，不发送网络请求。

## 1. GET /auth/consent：状态查询改为三个字段

成功响应改用新增的 `ConsentStatusViewResponse`，以及它的结果封装 `Result_ConsentStatusViewResponse`。

```json
{
  "status": "NOT_GRANTED",
  "identityReady": false,
  "policyVersion": "cross-border-preferences-v3"
}
```

三个字段均必返且非 null。查询不再返回 `backfillStatus`、`cleanupStatus`、`registrationAccepted`，也不返回 `consentProof`。没有同意记录时返回 `NOT_GRANTED`、`false` 和当前生效政策版本；已有记录时返回记录对应的政策版本。

新版查询结果的非零业务码分支规定 `data=null`；旧版复用的 `ConsentReply` 允许特定进度错误码携带进度数据。当前请求封装会拒绝非零业务码，未发现依赖该旧错误响应数据的读取逻辑。

这次精简仅针对 GET 查询。授权、撤回及登录过程中的进度响应仍保留六字段模型，不能全局删减 `ConsentViewResponse`。`identityReady=true` 或 `status=GRANTED` 仍不代表已取得登录会话。

当前前端有一项可见的不兼容：

- `frontend/src/api/service.ts:237` 的 `consent()` 仍声明为六字段 `ConsentViewResponse`。
- `frontend/src/pages/Settings.tsx:420` 仍展示“注册已接受”，并用 `c?.registrationAccepted ? "是" : "否"` 判断。真实三字段响应会被展示成“否”，将缺失字段误当作否定状态。
- `frontend/src/desktop/DesktopAccount.tsx:190` 在账号设置里复用这个组件，因此 PC 授权面板受影响。
- `frontend/src/demo/transport.ts:463` 的查询仍直接复用旧状态对象，可能带出 `registrationAccepted` 等额外字段，无法准确暴露上述差异。

适配时应为 `consent()` 使用三字段查询类型，移除不属于查询结果的“注册已接受”行，并让 Mock 的 GET 查询明确投影这三个字段；授权及撤回动作继续沿用各自的进度响应。

## 2. 三项登录/注册操作：loginId 改为 string

| 操作 | 旧契约 | 新契约 |
| --- | --- | --- |
| `POST /auth/login` | `string \| integer` | `string` |
| `POST /auth/register` | `string \| integer` | `string` |
| `POST /auth/phone/login` | `string \| integer` | `string` |

对应共享模型是 `SaTokenInfoResponse`、`PhoneLoginDataResponse`。当前应用登录逻辑使用 `tokenName`、`tokenValue`，未发现依赖 `loginId` 数字运算的业务代码；主要影响生成类型及响应校验。

## 3. 四项屏蔽操作：文档标记为已部署

```text
GET    /user/blocks
GET    /user/blocks/{userId}
PUT    /user/blocks/{userId}
DELETE /user/blocks/{userId}
```

旧文档标记“两站均未上线”；新文档说明 2026-10-26 已双站发布 V80、启用 `user.block schema 1`。屏蔽的上传者会在推荐候选截断前被过滤，关闭个性化推荐时仍生效。

这是既有路由的部署状态更新，路径、方法、参数和业务返回字段未变。当前前端已有 `blocks`、`blockStatus`、`setBlock` 封装、食友主页屏蔽入口及屏蔽名单页面。后续重点是用授权测试账号验证真实服务，不需要新增一套接口。这里的“已部署”来自 APIv3 文档，未在本次核查中实测。

个性化推荐开关及通用活动在旧文档中已经标记为已部署，本轮主要更新说明日期，不属于新增能力。

## 4. 文档格式与接入入口

OpenAPI 标识从 `3.1.0` 变为 `3.0.1`。大量 `type: [T, "null"]` 或 `anyOf` 可空表达改为 `nullable: true`；活动起止时间的排他下界写法也变化，但归一化后的边界不变。这些不计为业务字段新增、删减或约束变化。

当前下列入口仍以 APIv2 为基准：

- `frontend/package.json` 的 `api:generate`。
- `frontend/src/api/contract.test.ts` 的契约文件读取。
- `frontend/scripts/audit-api-coverage.mjs` 的覆盖率基准。
- `frontend/scripts/audit-api-v2.mjs` 的对比目标。
- 已生成的 `frontend/src/api/schema.d.ts`。

接入 APIv3 时，应同步调整当前契约基准、生成类型、查询页面和 Mock，再补三字段响应的回归检查。现有契约测试主要检查请求路径与必传参数，不能据此认定查询返回字段已经兼容。
