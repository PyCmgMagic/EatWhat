账号安全复核 3 项也返回未细化的 `Result_AnyResponse`，受相同多写开关控制。目录与资料同步管理接口受各自配置开关控制；文档声明存在不代表当前部署已启用。本轮没有通过真实写请求探测开关。

活动接口对应的是“地域美食”“年夜饭”两类固定内容；不能据此推断已有任意专题的目录、封面、时间范围和内容编排接口。活动发布返回 Void，不能套用普通菜品发布成功返回 `{id}` 的流程。

## 已接入接口仍有页面适配遗漏

`frontend/src/pages/Admin.tsx` 的 `AdminFoods` 仍沿用旧限制：只有 `user.verified === true` 且输入餐厅编号才读取菜品，并提示“v2 的菜品读取同时要求 verified”。最新 `GET /foods/list` 已允许游客读取，`restaurantId` 也可省略。因此这是后台页面对现有接口的使用遗漏，会拦住未认证的管理员读取，并缺少全站筛选入口；不是后端缺少全站列表。管理员编辑、删除仍应保留 admin 权限要求。

源码中的旧搜索、旧收藏、旧手机注册画板还有“待接入”文案，但当前 `/search`、`/favorites`、`/auth/register` 路由已由新组件接管，不应仅按这些旧文案重复判定功能未接入。

## 页面上未开放，且最新文档仍缺完整协议的能力

- 评论、回复、评论点赞：PC 本地 Mock 可演示，真实模式没有对应读写协议。
- 举报、意见反馈、店铺纠错提交。
- 登录设备列表、远程下线、屏蔽名单、自助注销账号。
- 通知偏好保存，以及独立的“关闭个性化推荐”开关；已接入的手动口味偏好不等于这两个能力。
- 完整换绑手机号流程；验证码 scene 中存在 `change` 不代表已有更换号码的提交接口。
- 他人的菜品列表；`/user/userInfo` 有分享数量，不提供具体列表，`/foods/list` 未声明作者筛选参数。
- 足迹清空；目前只有浏览历史查询。
- 任意专题目录/详情与编排、真实地图图层/选点/导航服务。

这些功能需要后端补协议或另选地图服务，不能用已有名称相近的接口替代。

## 建议接入顺序

1. 先补未登录撤回授权、认证方式明细，并修正管理页的旧菜品读取限制。
2. 补齐密码冲突及账号安全复核的响应定义、启用状态，再做恢复闭环。
3. 如果活动属于近期范围，接两类活动的浏览、详情、发布和点赞，并重新设计专题入口。
4. 区域定位、批量上传作为体验优化；同步冲突管理按运营需要单独安排。
