# EatWhat 后端 v2 接口整理

以 `EatWhat-backend` 的 `origin/feat/eatwhat-v2` 提交 `abda0149131a79479e72d01d6e12c597bae51b19` 为准，结合控制器、DTO 和服务规则核查。[后端 v2 原始 OpenAPI](EatWhat%20业务服务%20后端v2.openapi.json) 可直接导入接口工具。对照基线是迁移前前端使用的 [APIv7](EatWhat%20业务服务%20APIv7.openapi.json)。

| 统计 | 前端 APIv7 | 后端 v2 |
| --- | ---: | ---: |
| 路径 | 193 | 75 |
| HTTP 操作 | 224 | 87 |
| OpenAPI 模型 | 330 | 99 |

按 HTTP 方法和路径统计，16 项新增，71 项沿用地址，153 项旧操作未出现在 v2。16 项含学校邮箱两个 `GET` 改 `POST`。71 项同地址操作在两份文档中都有契约差异，具体接入以实际请求、响应和权限为准。87 项中有 8 项是学校回跳，业务客户端调用面为 79 项。

## 通用协议

- 公网由网关加 `/api`，直连应用使用表中的路径。登录态用请求头 `satoken: Bearer <tokenValue>`，令牌来自登录响应的 `data.tokenValue`。
- 业务 JSON 使用 `Result{code,data,msg,timestamp}`。业务成功和业务错误通常都是 HTTP 200，`code=0` 表示成功，无返回值的操作 `data` 为 `null`。路由不存在、方法不符、内容类型不符分别返回 HTTP 404、405、415。学校回跳用 HTTP 302。
- 普通列表以 `page`（从 1 开始）、`pageSize` 分页，返回 `currentPage`、`items`、`totalPages`、`totalItems`、`hasNext`。设备会话用 UUID `cursor` 和 `size`，返回 `devices`、`nextCursor`，设备时间字段为 ISO 日期时间。店铺、商圈、政策等 DTO 的时间字段使用毫秒时间戳。
- 向服务端请求短信、邮件时带腾讯人机验证请求头 `X-Captcha-Ticket` 和 `X-Captcha-Randstr`。密码登录在返回 `30015` 时完成人机验证后重试。密码错误与账号不存在均用 `30004`。

## 同路径的接入变化

### 账号、政策和用户

- `GET /auth/consent/policy` 返回 `{version, privacyText, crossBorderText, publishedAt}`。有已发布版本时，`POST /auth/register` 和所有 `POST /auth/phone/login` 都要传当前 `policyVersion`，手机验证码会在版本校验后才被消费。没传返回 `20005`，版本过期返回 `20009`。未发布政策时，政策字段为 `null`，注册和手机登录可省略版本。
- `POST /auth/login` 可选 `policyVersion`，登录成功后记录同意。有效会话收到 `20009` 时保留令牌，通过 `GET /auth/consent/policy` 取新正文、`GET /auth/consent` 取状态、`POST /auth/consent/grant {policyVersion}` 提交。状态为 `{agreedVersion, agreedAt, currentVersion, required}`。这些接口与 `POST /auth/logout` 在重新同意前仍可用。管理员发布新版本后也需重新同意。登录前的 `20009` 则应更新登录或注册页面上的版本并重新提交。
- `POST /auth/checkUsername` 把 `userName` 放在 JSON 请求体中。登录、注册仍可接收 `username` 别名，同时提交时两者必须一致。登录和注册的 `device` 取 `WEB` 或 `APP`。
- `POST /auth/phone/code {mobile}` 用于登录和自动建号。`POST /user/getCode {mobile}` 与 `POST /user/bindMobile {mobile, code}` 用于给尚未绑定手机号的账号补绑。已绑定时走三步换绑。忘记密码且有绑定手机时，先用手机验证码登录，再调用 `/auth/password/code`、`/auth/password/reset {code, newPassword}`；无手机号时由管理员设临时密码。
- `GET/POST /auth/sdu?client=web` 返回 `{url, expiresIn}`，`expiresIn` 以秒计。学校回跳通过 302 交给浏览器，成功时结果地址带 `result=success&code=0` 和 5 分钟有效的一次性 `ticket`，失败时带 `result=failure` 和对应业务码。前端用原账号提交 `ticket` 确认后再刷新认证状态。`GET /auth/verify` 返回 `{verified, method, phoneBound, usernameSet, passwordSet}`，学校邮箱也要通过登录态确认。
- `GET /auth/sessions` 返回的设备条目为 `{sessionId, device, issuedAt, expiresAt, current}`。撤销单设备及其他设备都返回 `null`，两项均无需 JSON 请求体。`POST /auth/username/set` 也返回 `null`，成功后重新读取用户资料。
- `GET /user/info` 去掉等级、经验、家乡和封禁详情，新增 `fansVisible`、`followingsVisible`。`GET /user/userInfo` 要登录，去掉等级、获赞和发布计数，新增 `gender`、`signature`、`blocked`。粉丝与关注列表的 `userId` 省略时读取自己，隐私关闭时按计数可空处理。
- `/user/list` 增加 `keyword`。`POST /user/ban/{userId}` 无请求体，封禁持续到解封。禁止封禁或重置自己及其他管理员。`GET /admin/summary` 只返回 `totalUsers`、`todayUsers`、`verifiedUsers`、`verifiedRate`。

### 店铺、收藏、地图和推荐

- `POST /restaurant/add` 要求 `name`、`address`、GCJ-02 `gcjLng`、`gcjLat` 和 `kind`。图片请求字段 `picture` 是一个已完成上传的 key。`kind` 取 `food` 或 `drink`，`mealTimes` 默认午餐和晚餐，`priceBand` 取 `UNDER_15`、`FROM_15_TO_30`、`OVER_30`，`categories` 最多 2 项，`tags` 最多 3 项，`deliveryEnabled` 默认 `false`。新增返回 `{id}`；附近 100 米同名店铺或 POI 已占用返回 `40004`。
- 店铺发布和编辑直接生效。认证用户和管理员可编辑及恢复版本，只有管理员可删。`PUT /restaurant/edit/{id}` 按提交字段修改，返回 `{id, revisionId}`，无实际变更时 `revisionId=null`。`picture`、`poi`、`priceBand` 传空字符串可清除，`categories`、`tags` 传空数组可清除。
- 店铺读接口返回单个 `pictureUrl`、`permanentlyClosed`、`dineIn{rate,count}`、`delivery{rate,count}`、`myRatings{dineIn,delivery}`，旧菜品关联字段、旧单一推荐率和 WGS84 `location` 已去掉。`rate` 范围是 0–1，无评价时为 `null`。游客的 `myRatings`、`isFavorite` 为 `null`。
- `GET /restaurant/search` 与 `/restaurant/browse` 使用同一查询。`categories` 改为店铺品类，可与 `tags` 重复传参或用逗号分隔，各自命中任一。`delivery=true` 匹配开通外卖或有外卖评价的店。`priceBand` 按店铺价位筛选，`recommendedOnly=true` 要求任一场景至少 3 条评价且推荐率达到 70%。`radius` 大于 0 且不超过 20000 米，需要成对传入坐标。
- `GET /restaurant/favorites` 及 `favoritesOnly=true` 需要登录，默认按收藏时间倒序，即 `FAVORITED_AT`。按距离须传坐标并显式指定 `DISTANCE`。普通浏览有坐标默认 `DISTANCE`，无坐标默认 `NEWEST`。
- `PUT /restaurant/{id}/rating` 提交 `{scene, rating}`，`scene` 为 `dine_in` 或 `delivery`，`rating` 为 `RECOMMEND` 或 `NOT_RECOMMEND`。`DELETE` 必须带 `?scene=`。两个操作均返回本人两个场景的评价，未评价的一项为 `null`。提交评价与收藏需要认证或管理员，取消只要求登录。
- 店铺商圈由后端按 GCJ-02 坐标计算。`/hub/add`、`/hub/edit/{id}` 接收 `boundaryGeoJson` 字符串，支持 Polygon、MultiPolygon 或仅包装一个此类几何的 Feature / FeatureCollection。读取的 `boundary` 为 GCJ-02 MultiPolygon 对象或 `null`，旧 WGS84 `center` 已去掉。商圈改动自动重算店铺归属，`GET /campus/list` 只返回开放校区。
- `/recommend` 以店铺为推荐单位，`scene` 默认 `dine_in`，`kind` 默认 `food`，`mealTime` 省略时按北京时间判断，可用值为 `breakfast`、`lunch`、`dinner`、`night`。游客可以读取，登录后才应用偏好、当日去重与不感兴趣。有坐标时堂食默认搜索 3000 米，外卖 5000 米。`PUT /user/recommendation-profile/preferences` 整体覆盖 `{likedCategories, likedTags, dislikedTags, priceBand, maxDistance}`，省略的字段清除。忌口由 `dislikableTags` 提供，目前为辣、麻，同一口味不能同时喜欢和忌口。`maxDistance` 取 100–20000 米，只应用于堂食。`DELETE` 返回 `null`。

### 图片上传

`POST /upload/presign` 提交 `{contentType, fileSize, biz}`，返回 `{putUrl, key, expireAt}`。批量接口提交 `{biz, files}`，最多 9 张，按请求顺序返回 `files`。向签名地址 PUT 原始字节，类型和长度须与申请时一致，然后 `POST /upload/complete {key}` 取得 `{key, url, size, contentType}`。业务表单引用本人已完成且用途匹配的 key。

支持 JPG、PNG、WebP、GIF。`avatar` 上限 5 MiB，`restaurants` 和 `feedback` 上限 10 MiB。申请 `restaurants` 上传签名要求 `verified` 角色，管理员也需有该角色。`feedback` 目前只有上传用途，反馈业务接口仍待实现。

## 旧前端入口如何处理

| 分类 | APIv7 调用与 v2 对应关系 |
| --- | --- |
| 推荐首页 | `/foods/recommend` 换为 `/recommend`、`/recommend/pick`。前端现有 `Food` 卡片、菜品转盘及详情链接需要改用店铺模型 |
| 账号页 | `/auth/getCode` 换为 `/auth/phone/code`，`/user/mobile/commands*` 换为三步换绑。重做政策同意、`20009` 和学校确认。`/auth/sessions/{commandId}/resume`、`/status` 退出接入 |
| 管理页 | `/admin/consent/policy` 换为 `/admin/consent/policies` 的发布、列表、详情。去掉手动商圈重绑、限期封禁和旧账号冲突审核入口 |
| 暂缓 | 菜品管理与发布、菜品收藏和标签、评论和晒图、校园专题、活动、提交审核。v2 暂无这些页面依赖的业务路由 |
| 待实现 | 推送、通知及通知卡片、反馈、浏览历史、使用统计、远程配置、活跃统计。浏览历史按分支规则计划保留 30 天，通知排在其他模块之后 |
| 移除 | 跨站同步 `/admin/sync/*`、省市查询、账户注销、旧密码冲突恢复与安全审核、成长经验、推荐个性化开关、旧同意 proof 和撤回接口。使用统计随政策同意启用，独立开关不在 v2 范围 |

迁移前的差异可对照 `frontend/src/api/service.ts`、`v4.ts`、`client.ts`，以及依赖 APIv7 的路由和权限规则。`checkUsername` 当前用 query，学校邮箱当前用旧 GET，取消评价缺少 `scene`，首页推荐按 `Food[]` 消费。后端分支部署文档规定用新数据库，旧账号和业务数据不迁移，测试环境应使用 v2 账号与数据。

## OpenAPI 与源码的差异

| 位置 | 按源码接入 |
| --- | --- |
| `POST /admin/users/{userId}/password` | 生成器把 `AdminDtos.ResetPassword` 和 `ContactDtos.ResetPassword` 合并。管理员提交 `{password}`；`{code, newPassword}` 仅用于 `POST /auth/password/reset` |
| `GET /auth/consent/policy` | 生成器合并了公开和后台两个 `ConsentPolicy`。公开响应只有 `version`、`privacyText`、`crossBorderText`、`publishedAt`；后台模型才有 `id`、`publishedBy` |
| 学校回跳 | OpenAPI 默认标了 200。`VerificationController.callback` 实际发送 302，登录后需另发 `POST /auth/sdu/confirm` |
| 服务层条件 | 生成稿缺少已发布政策时 `policyVersion` 必填、店铺 `kind` 等服务层约束。上传要求和登录触发的人机校验也要结合控制器与服务规则处理 |
