# APIv2 接口变更与腾讯人机验证接入分析

日期：2026-10-26。对比依据为 [新版 APIv2](<EatWhat 业务服务 APIv2.openapi.json>)、[旧版 API](<EatWhat 业务服务 API.openapi.json>)、当前前端源码，以及[后端提供的腾讯 CAPTCHA 说明原文](tencent-captcha-20261026.md)。文中的部署情况来自接口文档，不代表本轮已经实测生产服务。

## 1. 结论

这次有影响主流程的兼容性变更，需要先修复登录、政策、昵称、推荐返回结构和验证码发送，再接入新增功能。不能只生成一次新类型就认为迁移完成。

| 对比项 | 结果 |
| --- | --- |
| OpenAPI 版本 | 3.0.1 → 3.1.0 |
| HTTP 方法与路径组合 | 126 → 136 |
| 新增 / 移除 | 新增 26 项，移除 16 项，净增 10 项 |
| 新增构成 | 12 项非活动操作，14 项活动及活动管理操作 |
| 当前已接入的请求操作 | 本地捕获 98 次，全部仍能匹配新版路径和 HTTP 方法 |
| 必传参数检查 | 8 个现有入口缺少新版必传字段或请求头，见下文 |
| 类型变化 | 新增 39 个 Schema、移除 14 个；大量响应补齐 required、null 和条件响应约束 |

保留的 110 个操作展开后均有结构差异，主要受公共响应模型收紧影响，**不等于 110 个接口都改了业务逻辑**。路径仍存在也不代表请求字段、返回结构和实际部署均已兼容。

现有 `frontend/package.json` 的 `api:generate`、`src/api/contract.test.ts` 和旧审计脚本仍指向旧 JSON。已有 Mock 与旧契约测试无法检出本次全部变化。

## 2. 优先修复的兼容性问题

### 2.1 登录参数与展示昵称正式分离（P0）

| 场景 | 旧契约 / 现有代码 | 新契约 | 前端影响 |
| --- | --- | --- | --- |
| `POST /auth/login` | Body：`username` | Body：`userName` | 密码登录请求缺少必传字段 |
| `POST /auth/register` | Body：`username` | Body：`userName` | 注册请求缺少必传字段 |
| `POST /auth/checkUsername` | Query：`username` | Query：`userName` | 查重失败；仍是普通请求参数，不改为 JSON Body |
| `POST /auth/consent/withdraw-with-password` | Body：`username` | Body：`userName` | 密码撤回授权请求不兼容 |
| `PUT /user/updateInfo` | 修改昵称：`userName` | 修改昵称：`displayName` | 保存昵称会发送旧字段；该字段可选，因此必传检查不会自动发现这个问题 |
| `GET /user/info` | 把 `userName` 当昵称 | `displayName` 是昵称；`userName` 是唯一登录名，可为 null；新增 `hasUsername` | 个人中心、头像首字、资料编辑、账号安全需要分别使用正确字段 |
| `GET /user/userInfo`、关注/粉丝列表 | 读取 `userName` | 改为 `displayName` | 食友主页、列表姓名及搜索会显示为空或退化为占位文案 |
| 管理员用户列表 | 只依赖 `userName` 展示用户 | 增加 `displayName`，登录名可为空 | 应分开展示昵称与登录标识 |

密码登录示例：

```json
{ "userName": "student_1", "password": "<用户输入>", "device": "WEB" }
```

修改展示昵称，不修改登录名：

```json
{ "displayName": "今天也要好好吃饭" }
```

登录名注册规则仍是 3–10 位字母、数字或下划线，并有排除纯手机号等约束；展示昵称是可重复的 2–12 字符，不能把两套校验规则混用。用户模型中的 `hasPassword` 与 `hasUsername` 也不能互相替代。

主要涉及：`api/service.ts`、`desktop/DesktopAccount.tsx`、`mobile/App.tsx`、`mobile/bridge.tsx`、`desktop/profile.ts`、`desktop/DesktopProfile.tsx`、`desktop/Desktop.tsx`、`desktop/DesktopCommunity.tsx`、`features/ProfilePeople.tsx`、`features/AccountExtras.tsx` 及 Mock 数据。

### 2.2 政策接口结构已改变（P0）

`GET /auth/consent/policy` 新版成功响应：

```json
{
  "code": 0,
  "data": {
    "version": "cross-border-preferences-v3",
    "url": "/api/policies/cross-border-preferences-v3.html"
  },
  "msg": "ok",
  "timestamp": 1792763739329
}
```

当前 `api/consent.ts` 与 `features/Consent.tsx` 依赖 `policyVersion`、`notice.documentPath`、`notice.documentSha256` 等旧字段；新版不再提供这些字段。结果是政策识别为空、正文地址无法解析，`ready/canSubmit` 不能成立，登录注册可能在同意环节被阻断。

迁移要点：

- 政策读取模型使用 `version/url`；同意提交仍分别使用 `consentPolicyVersion` 或 `policyVersion`，值来自 `data.version`。
- `url` 可为 HTTPS URL 或站点绝对路径。示例已经含 `/api`，不能再次拼成 `/api/api/policies/...`。按站点 origin 解析绝对路径，不能沿用旧版仅接受 `/policies/*.html` 后再拼 API 前缀的规则。
- `url=null` 需要展示“政策正文暂不可用”的明确状态；不要伪造同意，也不要使用另一版本的静态正文替代。
- 政策发生变化后重新阅读、重新勾选的保护继续保留；正文从返回 URL 加载并沿用已有净化逻辑。
- `siteMode`、`temporaryAuthenticationRelay`、`ordinarySessionRequiresAuthorization` 和旧 `notice` 不能继续作为必返字段使用。
- 个人授权状态 `ConsentViewResponse` 移除了 `epoch/revision`，新增的管理员政策配置又有自己的 `revision`，二者不能混用。

### 2.3 推荐接口由数组改为分页对象（P0）

`GET /foods/recommend` 的 `data` 从 `FoodVOResponse[]` 变为 `PageResult_FoodRecommendationVOResponse`：

```json
{
  "currentPage": 1,
  "items": [ { "id": 1, "name": "示例菜品" } ],
  "totalPages": 1,
  "totalItems": 1,
  "hasNext": false
}
```

以上只演示外层形状，省略了菜品模型的其他必返字段。

现有 `api.recommend()` 声明为 `Food[]`，首页使用 `.length/.map/.filter/.slice` 和数组下标。直接接新版会造成空态误判或运行错误。建议适配层明确读取 `data.items`，保留首页“换一组”的批次行为。

新版区分了普通 `FoodVOResponse` 与 `FoodRecommendationVOResponse`：普通列表/详情的餐厅地址、餐厅坐标和商圈字段固定为 null；推荐 VO 才允许填充实际值。更新类型时需要公共展示模型或明确的推荐模型，不能用强制类型转换掩盖这项差异。

注意：推荐接口仍只列出 `size/limit` 等参数，没有 `page` 参数。不能仅因返回分页模型就接一个未经定义的“下一页”请求，元数据语义建议后端进一步明确。

### 2.4 验证码发送新增强制人机验证（P0）

当前 4 个已接入的发送方法 `phoneCode/passwordCode/sendMobileCode/sendEmail` 均未携带新版 CAPTCHA 请求头；传输层 `RequestOptions` 目前也没有自定义 `headers` 或 `cache` 选项。

需要统一接入第 4 节的验证流程，而不是在某一个登录页面单独增加滑块。

### 2.5 菜品重复名称响应需要保留业务数据（P1）

新版创建及编辑相关响应明确描述 `code=40016` 和 `data.id`，用于引导用户查看同店已存在的菜品；编辑接口使用 `FoodEditReply`，正常 `code=0` 的 `data` 则为 null。

当前 `createRequester()` 对非零 code 直接抛 `ApiError`，错误对象只保留 code/status/message，会丢失 `data.id`。后续应为这类操作增加明确的领域结果处理或保留受控的错误数据，显示“查看已有菜品”，同时保留未提交草稿。40016 不能视为编辑成功，也不能自动再次创建。

### 2.6 响应类型更新不能只机械替换（P1）

- OpenAPI 改为 3.1.0，采用 `type: ["string", "null"]`、`anyOf`、`if/then` 等约束。本轮已用项目现有 `openapi-typescript 7.13.0` 成功生成预览类型，未覆盖运行中的旧 `schema.d.ts`。
- 登录成功、待同意、身份未就绪与普通失败成为更明确的联合响应；当前 `classifyAuth()` 已检查 `code=0 + isLogin=true + tokenName/tokenValue`，这部分运行时判断应保留，不能把同意凭证当登录令牌。
- `pictureUrl/pictureKeys`、`accountId=null`、生日日期字符串等要继续按各自含义使用；游客仍不能因此获得作者管理权限。
- `removeBackground` 仅保存开关，并未实现自动去背景。饭点、舞台色和裁剪字段在旧文档已有，不应误报为这次新增加的前端功能。
- 更新类型、契约测试来源、Mock 与业务组件必须同步进行。旧契约测试通过不代表 APIv2 已兼容。

## 3. 新增的非活动接口与页面机会

| 新增操作 | 对应页面与行为 | 注意事项 |
| --- | --- | --- |
| `GET /auth/captcha/config` | 所有受保护的发送动作 | 每次验证重新获取，禁止缓存；详见第 4 节 |
| `POST /auth/username/set` | 手机注册后的可跳过引导、账号与安全 | 首次设置唯一登录名；使用 `/auth/password/code` 的验证码，可同时设置初始密码；成功返回 `reauthenticationRequired=true`，需要清理会话并重新登录；不能改已有自选登录名 |
| `GET /foods/by-user/{userId}` | 食友主页“TA 的分享” | 已有页面仍显示“分享列表暂未开放”，现在可接分页和筛选；要求登录，未要求 verified；互动和私有标签按当前访问者计算 |
| `DELETE /history/browse` | 足迹清空 | 不传 `targetType` 清空菜和店；传 `food/restaurant` 清空对应分栏。前端“店”标签不能直接传 `shop`；成功为 Void，清理全部相关分页缓存 |
| `GET/PUT /user/recommendation-settings` | 隐私设置中的个性化推荐开关 | Body 为 `{personalized:boolean}`。文档标注 V79 已部署；关闭不删除历史或口味偏好，也不等同于撤回跨站授权 |
| `GET /user/blocks` | 设置中的屏蔽名单 | 分页返回被屏蔽者 `userId/displayName`；名称可能为空，仍需支持按 ID 解除 |
| `GET/PUT/DELETE /user/blocks/{userId}` | 食友主页屏蔽/解除、状态展示 | 私人屏蔽与管理员封禁不同；文档明确 V80 **尚未发布到两站**，需要能力门槛与未开放状态，不能直接宣称线上可用 |
| `GET/PUT /admin/consent/policy` | 管理后台政策配置 | GET 返回 `version/url/revision`；PUT 提交 `version/url/expectedRevision`。仅权威站可写，修订冲突需重新读取；此接口只保存正文地址，不上传政策文件 |

上述共 12 个 HTTP 操作。屏蔽虽然有了契约，目前仍应保持“未开放”的真实线上状态；推荐开关、TA 的分享、足迹清空不应继续笼统地写“没有接口”。

先前跳过的密码冲突恢复与账号安全复核也有了补充：挑战/重置/决策提交的 `Result_AnyResponse.data` 现在明确为 null，安全复核列表则明确为 `ReviewSummaryResponse[]`，包含 `eventId/subjectId/field/state`。这消除了此前部分协议缺口，但仍沿用之前暂缓该模块的范围决定，不在本次分析中自动恢复开发。

## 4. 腾讯 CAPTCHA 的准确接入范围

### 4.1 保护的是发送动作

| 方法与路径（相对既定 baseURL `/api`） | 用途 | 当前前端情况 |
| --- | --- | --- |
| `POST /auth/phone/code` | 手机验证码登录/自动注册的短信 | 已接入；`features/Account.tsx`，PC/移动端共用 |
| `POST /auth/password/code` | 设置登录名、设置/修改密码的绑定手机验证码 | 已接入；`features/Account.tsx` |
| `POST /user/getCode` | 绑定手机等 scene 短信 | 已接入；`pages/ProfileExtras.tsx` |
| `GET /auth/sendEmail` | 学校邮箱认证邮件 | 已接入；桌面账号页、移动桥接及旧设置页均有调用 |
| `POST /auth/getCode` | 已认证账号旧短信入口 | 现有适配层未提供，不要误当作匿名登录验证码接口 |
| `POST /auth/password-conflict/challenge` | 密码冲突恢复邮件 | 此前按范围暂缓，后续启用时也必须接验证 |

不是所有登录/注册提交都需要再弹一次验证码。密码登录、用户名注册提交、`/auth/phone/login`、手机号绑定提交、密码重置提交，不能仅凭“属于认证模块”就额外加入文档未要求的 CAPTCHA。

### 4.2 一次完整流程

1. 用户点击发送，先做表单、登录/认证门槛、必要的政策同意和重发间隔检查，然后锁住本次动作。
2. 按需加载国际站官方 SDK，地址为 `https://ca.turing.captcha.qcloud.com/TJNCaptcha-global.js`。脚本加载可以共享；验证配置、配置 Promise、实例与票据不能共享。
3. 直接请求 `GET /auth/captcha/config`，使用 `cache: "no-store"`；不要放到页面初始化、React Query 全局缓存或自动预取中。
4. 检查 `enabled/provider/appId/scriptUrl/aidEncrypted/aidEncryptedType/expiresAt`。生产开启时初始化参数不能为 null；`aidEncryptedType` 为 `cbc`，`expiresAt` 是 **Unix 秒**，比较时乘 1000。其有效期不是 ticket 的有效期。
5. 创建全新的 `TencentCaptcha(container, appId, callback, options)`，传入本次 `aidEncrypted`、`aidEncryptedType` 和适当语言，再调用本实例的首次 `show()`。
6. 用户取消（`ret=2`）时结束流程，不发送、不启动倒计时。异常、无有效 ticket/randstr 或 `trerror_` 容灾票据也不发送。
7. 前端成功回调必须是 `ret=0`、无异常 `errorCode`，且同一次回调同时提供 ticket/randstr；以两个请求头发给对应业务接口。
8. 由业务后端核查腾讯票据。业务响应 `code=0` 后才提示已发送；短信此时才启动已有 60 秒倒计时，邮箱更新发送状态。
9. 无论成功、限流、业务失败还是网络中断，均结束并销毁实例、丢弃票据与初始化参数。重试必须重新获取配置、新建实例。卸载/切换路由也清理，迟到或重复回调不得再次发送。

```http
X-Captcha-Ticket: <同一次回调的 ticket>
X-Captcha-Randstr: <同一次回调的 randstr>
```

业务 Body、Query、登录头和 scene 保持原协议。不能把 ticket 放 URL、持久化存储、日志或普通会话里，也不能让对象存储 PUT 携带这些头。浏览器不负责 TC3 签名、AppId 加密或腾讯云服务端票据核查，更不能接收 AppSecretKey、SecretId、SecretKey。

后端说明要求 `CaptchaCode=1` 且未判为恶意才发送；HTTP 200 和前端 `ret=0` 都不能替代此检查。腾讯官方文档提供的通用容灾示例不能覆盖本项目禁止 `trerror_` 放行的业务契约。[腾讯国际站 Web 接入说明](https://intl.cloud.tencent.com/zh/document/product/1159/49680)、[AppId 鉴权与一次一密规则](https://cloud.tencent.com/document/product/1110/128489)支持 SDK、参数和单次 IV 的接入方式；不复制其中日志输出或容灾放行示例到业务代码。

### 4.3 错误处理

| 业务 code | 含义与前端处理 |
| --- | --- |
| `30015` | 缺票据/随机串；结束本次流程，重新验证 |
| `30016` | 无效、过期、已用或风险拒绝；清空本次材料，重新验证 |
| `50004` | CAPTCHA 配置或上游不可用；停止发送，保留表单并允许稍后重试 |
| `50001` | 新说明中的跨站验证码归属/通信不可用；不是验证码校验成功，更不能在另一站绕过原流程 |

不要用自动重试机制复用票据或重新发送短信。验证码本身的 5 分钟有效期、跨站共享 60 秒发送间隔、最多 5 次错误尝试继续由后端控制；跨站使用不要求客户端提交签发站。

### 4.4 代码接入位置

| 层次 | 建议改动 |
| --- | --- |
| `api/client.ts` | 为必要请求提供受控 headers/cache/取消能力；保留现有 token、HTTP 与 code 双重判断 |
| `api/service.ts` | 新增本次配置读取；发送方法接收本次票据对，并正确保留 Body/Query/登录要求 |
| 公共 CAPTCHA 模块/Hook | SDK 按需加载、一次一流程、取消销毁、过期、重复回调、卸载和错误状态 |
| `features/Account.tsx` | 手机短信和密码短信按钮进入统一验证流程；政策检查仍先于验证码发送 |
| `pages/ProfileExtras.tsx` | 绑定手机发送入口；不把验证码用途改成手机登录 |
| `desktop/DesktopAccount.tsx`、`mobile/bridge.tsx` | 邮箱认证发送；继续保留 GET 方法，发送请求也应禁用缓存 |
| Mock 与测试 | 隔离地模拟配置、取消、成功、失败与重复回调；不得让测试票据或测试关闭逻辑进入真实环境 |

如果生产前后端跨域，CORS 需要允许新增的两个 `X-Captcha-*` 头；仅在本地同源代理下成功不能证明此项已满足。需补查手机、平板、PC 的 SDK 弹层层级、键盘与横竖屏；真实人工挑战成功后的短信/邮件投递，后端说明也标记为尚待前端端到端验收。

## 5. 文档里仍需后端确认的事项

1. **资料冲突读取与裁决模型不对应。** `ConflictResponse.heads[]` 已明确为 `{id,value,vector}`，并写明 id 用作 `selectedHeadId`；但两个资料裁决接口仍引用 `ResolveRequestRequest`，结构是 `candidates[{gid,revision,contentHash}]`、`winnerGid` 等，未定义 `selectedHeadId`。不能从现有 heads 安全推出旧版 candidates。当前 `api/sync-management.ts` 与 `pages/AdminSync.tsx` 正是旧式候选版本表单，需要后端提供一致的提交 DTO/真实样例；不要猜测映射或内容摘要。
2. **推荐分页元数据语义。** 已返回 PageResult，但没有 page 参数；前端可先取 items 保留换一批行为，完整分页语义不应自行创造。
3. **文档版本与部署分离。** `info.version` 仍是 `tencent-captcha-20261024`，内容已包含 10 月 26 日 V79/V80 状态；不能仅凭版本字符串判断能力。屏蔽明确未部署，部分账号/同步接口还受配置开关控制。
4. **政策管理写权限与冲突提示。** 仅权威站可写，但读取模型未提供可写能力标记。应约定权限/修订冲突错误处理；读取成功不等于可以保存，不能自动刷新 expectedRevision 后覆盖重试。

`servers` 在新旧 JSON 中均为空，正文说明约定 `/api`。这不是新改动；现有后端 baseURL 继续使用 `https://v50to.you/api`，文档路径按真实映射拼接，省市字典路径中的额外 `/api` 不自动去重。

## 6. 建议接入顺序与验收

1. **先完成兼容层迁移：** 切换类型生成及契约测试来源；修复 `userName/displayName`、政策 `version/url`、推荐 items；同步修改 Mock，防止演示仍返回旧格式而掩盖错误。
2. **完成公共 CAPTCHA 后覆盖所有当前发送入口：** 先验证取消、失败、重复回调和路由卸载，再由测试用户完成双站真实人工挑战。发送短信/邮件需另按明确的联调授权执行。
3. **接入明确可推进的业务：** 首设登录名及强制重新登录、TA 的分享、足迹清空、个性化开关、管理员政策设置。同步处理分页、加载、空态、错误和缓存失效。
4. **屏蔽模块按部署能力推进；资料冲突按统一后的契约修复。** 地域美食、年夜饭及通用活动模块继续沿用此前不接入的范围；密码冲突和账号安全复核保持此前暂缓决定，已补齐的协议记录在此供后续使用。

主要验收项：

- 新版登录/注册/查重/密码撤回发送正确字段；昵称保存不改变登录名；手机账号 `userName=null` 时仍正常展示 displayName。
- 政策仅返回 version/url 时可阅读和同意；站内 `/api/policies/...` 不重复前缀；版本变化需重新同意，url=null 不放行。
- 推荐返回分页对象时 PC/手机首页、分类、换一组正常；空 items、普通详情的 null 元数据及游客作者权限正确。
- CAPTCHA 的取消/过期/重复回调/配置失败/SDK 失败/票据错误均不发送；每次重试取新配置；业务成功才计时，失败保留手机号和表单。
- 清空足迹后各分页与分栏不残留旧缓存；个性化关闭不清理口味/历史；屏蔽未部署时保持真实未开放状态。
- 首次设置登录名成功后清理本地会话和私有查询缓存，再引导重新登录，不能继续沿用已作废令牌。
