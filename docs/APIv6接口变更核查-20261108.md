# APIv6 接口变更核查

本文保留接入前的核查结论。后续已按用户要求完成规划与前端接入，当前实施状态、验证结果及边界见 [APIv6 接入规划与验收](APIv6接入规划与验收-20261108.md)。

核查日期：2026-11-08。以用户提供的 `EatWhat 业务服务 APIv6.openapi.json` 为最新文档，与当前前端使用的 `EatWhat 业务服务 APIv5.yaml` 对比，并检查现有适配层、认证与设置页面。

本次完成本地契约对比、源码检查和类型替换试跑。未调用真实业务接口，未切换应用生成源、开启功能、推送或部署。此前首页筛选去重、附近自动定位等未提交改动保留。

## 总体结果

| 项目 | APIv5 | APIv6 |
| --- | ---: | ---: |
| 路径数 | 178 | 184 |
| HTTP 操作数 | 204 | 212 |
| OpenAPI 声明 | 3.1.0 | 3.0.1 |
| 文档内部版本 | `source-contract-20261101` | `user-blocks-consent-20261026` |

新增 8 项 HTTP 操作，删除 0 项。归一化比较后，49 项已有操作存在结构变化，另有 155 项仅有文档变化；其中有大量重复传播的模型变化与鉴权声明变化，不代表 49 个业务功能都要重写。新增 10 个模型、调整 8 个已有模型、移除 7 个模型名。309 个本地 `$ref` 均可解析，212 个 operationId 无重复。

文档的 212 项操作均写有“2026-11-07 实现代码已部署到唯一海外业务站”，同时明确注册路由仍受配置和账号状态约束。这是文档的部署声明，本次没有做线上能力探测，不能据此认定所有真人流程已验收。

## 新增能力

| 接口 | 权限 | 作用与接入注意 |
| --- | --- | --- |
| `POST /user/activity` | 登录 | 显式记录当天活动，无请求体；不能传用户 ID、日期或经验值。返回业务日期、首次活动标记、实际新增经验和成长进度。 |
| `GET /user/growth` | 登录 | 累计经验、等级、当前等级进度、下一等级门槛和满级状态。 |
| `GET /user/growth/ledger` | 登录 | 经验流水，按实际入账时间倒序；分页默认 20，page 为 1–10000，pageSize 为 1–100。 |
| `GET /admin/engagement/stats` | 管理员 | 指定日 DAU、该完整自然月 MAU、截至该日的最近 30 天去重活跃；日期默认 Asia/Shanghai 当天，不允许未来日期。 |
| `GET/POST /auth/callback`、`GET/POST /callback` | 文本声明公开 | 共 4 项学校回调操作，处理 `state` 和学校一次性 `code`，属于后端认证链路。 |

成长首版为 Lv.1–Lv.10，每天首次有效身份业务调用获得 5 经验；多设备、重试不会重复奖励，升级不扣经验。普通业务请求本身也会记录活跃，因此不能把 `/user/activity` 做成领取经验按钮或高频心跳。界面应使用服务端返回的等级门槛、经验和业务日期。

当前前端尚未封装以上 4 项客户端业务接口，也没有对应等级经验或活跃统计页面；4 项回调不应当作为浏览器普通 API 写请求调用。

## 对现有前端的直接影响

### 1. 首次设置登录名不再要求重新登录

`POST /auth/username/set` 的说明变为：成功后 `data.reauthenticationRequired=false`，当前设备和其他设备会话均保留。用户名、初始密码仍在同一事务中提交，已有密码不能被首次设置入口覆盖。

当前 `frontend/src/features/ApiV2.tsx` 的 `UsernameSetup` 仍无条件调用 `clearLocalSession()`，随后跳转 `/auth/password`，页面文案也写着“设置后需重新登录”。`frontend/src/demo/transport.ts` 的模拟返回仍为 `reauthenticationRequired: true`。

这是优先修复项：按服务端返回判断是否需要重新认证；无需重新认证时刷新账号信息和显示成功状态，保留会话。演示响应、页面文案和回归脚本需一并更新。

### 2. 注销账号新增内容保留选择

`LifecycleCancellationControllerRequestRequest` 新增可空布尔字段 `deletePostsAndComments`：

- 省略、null 或 false：匿名保留已发布帖子、评论的正文和图片，正常用户仍可点赞回复。
- 仅 true：明确删除本人内容。
- 该选择绑定本次签名注销请求，同一请求重试不能更改。

当前注销页面只提交 `requestId` 和 `recoveryCapability`，按新契约会走“匿名保留内容”。现有说明只泛称可能清理数据，没有解释这个默认行为。接入时应提供清晰的内容保留选项；受理或结果不确定后固定本次选择，不能在重试时悄悄改变。

### 3. 学校认证改为固定回调地址和 code 交换

新发起的学校回调为 `/api/callback?state=...&code=...`，后端用 code 换取并验证学校凭据，不接受浏览器传入的 token。旧的路径 state 回调仍保留兼容。

前端发起方式仍是 `/auth/sdu` 返回 `data.url/expiresIn` 后打开该 URL；学校回调完成后才重定向到后端配置的网页/App 目标，客户端不能指定任意目标。文档中的学校回调地址和应用结果页是两个阶段，不能把 `/api/callback` 改成前端页面。

现有 `VerificationResult.tsx` 会用原会话重新查询 `/user/info`，并通过本地来源记录返回原页面；这与新文档要求一致。已有错误映射覆盖 30012、30013、50003。后续可以细化 50003 提示，使其同时包含学校 code 换取失败和凭据校验失败。

### 4. 菜品返回作者对象

`FoodVOResponse`、`FoodRecommendationVOResponse` 新增必返但可为 null 的 `user`，非 null 时为 `{ id, displayName }`；原 `accountId`、`uploaderName` 仍保留。

文档说明公开菜品保留作者 accountId，资料为占位或不可展示时 user 为 null。当前菜品卡片、详情继续读取 uploaderName，保留兼容；后续可以统一作者展示适配，正确处理 null，不把作者对象缺失当作请求失败。这个新模型不含头像或等级字段。

### 5. 类型与导出差异

- 两个登录响应的 `loginId` 从 `string | integer` 收窄为 `string`。当前登录功能依赖会话 token，不依赖 loginId 做数字运算；`service.test.ts` 的两个类型断言需更新。
- 7 个被移除的模型名包括查询 DTO 和旧 Result 别名，相关操作路径和查询参数仍在；当前前端没有直接引用这些模型名。
- Activity 的部分动态字段必填声明放宽，部分联合类型补充 `type: object`。活动功能仍维持项目既有排除范围。
- 恢复凭据安全方案改名为 `RecoveryCapability1`、`LifecycleRecoveryCapability1`，实际 HTTP 头仍是 `X-Recovery-Capability`、`X-Lifecycle-Recovery`，不应因为组件名变更而改请求头。
- 附近店铺搜索的参数结构未改变，仍使用 GCJ02 经纬度；本轮自动定位的坐标转换和查询方式符合新文档。
- 推荐响应仍描述为分页 data.items；项目已记录线上曾返回 data 数组，当前双格式兼容应保留，不能仅因文件升级删掉。

## 文档需要澄清的地方

1. **版本元数据滞后。** 文件包含 11 月新增能力，但 info.version 仍是 `user-blocks-consent-20261026`。本次依据实际内容而不是该字符串判断版本。
2. **servers 为空。** 根级描述写默认 `/api`，实际 `servers: []`。前端现有 API 基址应保留；文档导入工具需要显式配置 `/api`。
3. **鉴权文本与结构冲突。** 30 项操作写“公开/可选登录”，却只声明 `security: [{ SaToken: [] }]`，没有匿名分支：其中 23 项可选登录读取，另有 7 项公开回调或注销恢复操作。游客访问语义不能因导出格式而变成强制登录。现有守卫对读取不主动弹窗，公开写操作按摘要跳过；未来权限生成器应明确处理“可选登录”，也建议修正文档结构。
4. **部署标记不等于配置已开启。** 包括推送在内的操作都改成已部署说明，但仍受配置控制。当前按用户要求展示的“通知偏好·敬请期待”不应仅因新文档出现接口就自行打开。

## 验证与接入顺序

已用现有生成方式把 APIv6 类型写到 `output/api-v6-schema.d.ts`，在内存中替换类型文件执行完整 TypeScript 检查，应用源码和现有 schema 未被覆盖。诊断仅有 `frontend/src/api/service.test.ts` 中两处 loginId 类型断言，与上述收窄一致；这不代表运行时接口或新页面已完成接入。

建议后续顺序：

1. 同步类型生成、权限生成和覆盖审计的数据源，更新两个类型断言，并保留 `/api`、游客读取、认证结果核验等行为。
2. 优先修正设置登录名后的会话处理，以及注销页面的内容保留说明和选项。
3. 接入成长进度、流水和管理员活跃统计；需要前台活动回报时使用统一生命周期入口，避免各页面重复上报。
4. 针对新契约做隔离回归，再按实际配置验证对应功能；保留现有通知等待页，直到该功能另行接入验收。

机器报告位于 `output/api-v6-diff-20261108.json` 和 `output/api-v6-assessment-20261108.json`，临时类型及检查脚本也在忽略的 `output/` 中。契约差异可在仓库根目录复现：
