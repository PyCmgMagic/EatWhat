# 最新接口接入差异分析

分析日期：2026-10-23。

实施状态：本次已完成前台主流程接入，详见 [新版接口接入与验证](新版接口接入与验证-20261023.md)。以下差距和分批建议保留为接入前基线，并非当前未完成清单；复查脚本现已覆盖 81 个服务操作。当前逐项缺口请以 [未接入接口核查](未接入接口核查-20261023.md) 为准：126 项中 45 项尚无封装，另有 1 项已封装但当前页面未使用。

最新契约：`EatWhat 业务服务 API.openapi.json`，版本 `dual-site-multiwriter-v73-20261023`。旧 YAML 仅作为差异对照，不再作为新增工作的接口依据。

## 结论

需要接入，而且新版已经补齐了此前影响主流程的多项缺口。重点不只是增加新方法，还包括使用原有接口的新筛选条件、消费新的返回数据、调整游客权限和发布后的跳转。

按 HTTP 方法与路径统计，接口从 101 项增加到 126 项：新增 26 项，移除 1 项。新增操作包含回调别名和管理接口，不等于新增 26 个前台功能。移除的是未被当前服务层使用的 `GET /activity/{provinceId}/foods`。

本次通过模拟传输执行了当前服务层的 69 项调用：路径、方法和必填查询参数均能对应新版文档，没有远程请求。这只证明上述调用边界仍能匹配，不代表响应模型、权限、业务语义与真实服务均已兼容。

## 第一批：直接补齐现有产品主流程

| ------ | ----------------------------------------------------------- | --------------------------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------- |
| 高     | 全站菜品查询：`GET /foods/list`                             | 当前 `api.foods()` 强制传餐厅，只接了标签条件；搜索主要查店，首页分类只筛选当前推荐批次 | `restaurantId` 可省略；支持菜名关键词、区域 `hubId`、分类、价格区间、排序及标签，筛选交给服务端并正确分页           |
| 高     | 完整收藏筛选：`GET /foods/favorites`                        | 当前仅传页码，分类是本页过滤                                                            | 接入关键词、分类、预算、排序、系统标签及个人标签，分类能够覆盖全部收藏；筛选改变时重置分页                          |

| 高     | 新店创建：`POST /restaurant/add`                            | 当前按 Void 处理，成功后要求回到列表重新选店                                            | 消费 `data.id`，直接带入发布工作区，继续添加菜品                                                                    |

| 高     | 云端展示参数：创建/编辑菜品 DTO 与 `FoodVOResponse`         | 当前舞台色只存在本机，裁剪主要生成本地取景文件                                          | 接入 `mealTimes`、`stageColor`、`stageAlternates`、`coverCrop`；列表与详情消费同一份服务端展示参数                  |

全站列表支持 `NEWEST`、`PRICE_ASC`、`PRICE_DESC`、`POPULAR`；收藏还支持 `FAVORITED_AT`。所有条件先筛选再分页，标签数组内要求所有不同标签均匹配，不是任选一个匹配。未知价格不满足预算条件，价格排序时置后。

注意：`/foods/list` 没有声明饭点参数；饭点筛选已明确支持的是推荐接口，不能直接扩展成全站列表也支持。`campusId` 和 `hubId` 是两层不同编号，也不能混用。

## 第二批：账号闭环与偏好

| 能力与接口                                                              | 接入要点                                                                                                                                                                  |
| ----------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| 手机验证码登录/注册：`POST /auth/phone/code`、`POST /auth/phone/login`  | 新号码自动注册，旧号码直接登录；用 `data.newUser` 引导新用户，用 `tokenName/tokenValue` 建立会话。建议把原待开放的手机注册页整合为“手机登录/注册”，不再虚构第二次注册提交 |
| 验证码设置密码：`POST /auth/password/code`、`POST /auth/password/reset` | 两个接口都要求已登录且已绑定手机；按 `hasPassword` 区分设置初始密码与修改密码。没有密码时，密码登录/旧密码修改会返回 `30010 PASSWORD_NOT_SET`                             |
| 学校统一认证：`GET` 或 `POST /auth/sdu`                                 | 携带当前会话调用，读取 `data.url`、`expiresIn`，再用浏览器打开返回地址。不能只跳到固定配置地址，丢失本次认证状态                                                          |
| 一次性认证回跳：`/callback/{state}`、`/auth/callback/{state}`           | state 有效期 5 分钟且仅一次；这是后端回跳入口，应让认证方回到正确地址，再刷新个人认证状态。旧无 state 回跳明确返回 `30012`                                                |
| 推荐偏好：`GET/PUT/DELETE /user/recommendation-profile/preferences`     | 可增加“喜欢/不喜欢的口味标签”设置，保存 `likedTags`、`dislikedTags`，并支持清空手动偏好。它与通知偏好是两个功能，不能把通知设置的待开放标记一起移除                       |

手机登录验证码规则已明确：同一手机号 60 秒一次，5 分钟有效，连续错误 5 次需重新获取；验证码须回签发站使用。跨站同号冲突返回 `ACCOUNT_SECURITY_CONFLICT`，不能在前端自动合并账号。

密码找回要分情况：上述短信设置密码接口不是匿名找回接口，但用户可先使用绑定手机号验证码登录，再在已登录状态设置密码。没有可用绑定手机号且未登录时，普通自助找回仍缺完整流程。

## 需要同时调整的兼容性与权限

1. **更新类型与契约测试来源。** `frontend/package.json` 的生成命令、`src/api/schema.d.ts`、`src/api/contract.test.ts` 仍基于旧 YAML。后续正式迁移应同时切换到新版 JSON，再调整服务层、Mock 与拦截测试，不能只换文档名称。
2. **重新划分浏览与操作门槛。** 推荐、菜品列表/详情、菜品标签读取、餐厅搜索/目录/详情、Hub 与校区目录均允许游客。我的分享、收藏及收藏操作只需登录；点赞、发布、作者编辑删除和个人标签管理仍需 verified。PC `DesktopGate` 和移动端 `publicScreens/needsVerification` 都要同步调整，不能统一要求学生认证，也不能统一放开所有按钮。
3. **区分展示 URL 与存储 key。** `pictureUrl` 现在明确是可直接展示的 URL，可能是临时签名地址；新增 `pictureKeys` 用于编辑保留图片。编辑请求中的 `pictureUrl` 传 key，不能把签名 URL 写回。签名失效后应重新请求列表或详情。历史非 `foods/` 引用应不提交图片字段以保留，或重新上传迁移。
4. **使用稳定的颜色枚举。** 舞台色是 `broth/chili/mango/porcelain/bamboo/redoil/soy/matcha/tomato`，当前代码存的是 HEX，需要映射；两个 `stageAlternates` 必须恰好两项。不能继续把只存在本机的色值当作已云端保存。
5. **统一新字段和表单限制。** 创建价格为 0–999999.99、两位小数；说明最多 2000 字。昵称为 2–12 字、签名最多 255 字；当前原型采用更严格的 3–10 字和 30 字，是否保留属于产品选择，需要在两端统一。新生日模型是 `date` 字符串，现有时间戳兼容逻辑可留作旧数据保护。
6. **处理字符串错误码与登录状态。** 非 200 拦截响应可能只有 `{code: "…"}`，没有 `msg`；现有客户端能保留 code，但界面缺少对应解释与恢复入口。新增的无密码、手机未绑定、过期 state、账号安全冲突应有对应提示。旧会话协议切换后可能需要重新登录；临时 `consentProof` 与同步完成状态始终不能代替正式 token。
7. **注意短信权限不对称。** `/user/getCode` 仍要求 verified，`/user/bindMobile` 要求登录。绑定界面不能因为页面可打开就认为未认证账号一定能取绑定验证码；应按认证状态引导。
8. **保留网关前缀规则。** 文档说明默认 `/api`，`servers` 数组本身为空。现有 `/api` 网关与 `/api/location/*` 控制器前缀不能自动去重，仍需使用正确部署配置。

## 已有字段，但仍需要补充语义或响应样例

- `coverCrop` 给出 0–1 的 `centerX/centerY/diameter`，但没有说明相对原图还是裁后图、非方形图如何定义直径、是否仅影响第一张封面。应先明确，避免把本地裁剪后的图片再裁一次。
- `removeBackground` 有读写字段，但没有明确抠图的处理时机、产物和失败行为；只能确认契约有开关，不能据此宣称自动抠图已经可用。
- 推荐偏好标签没有词表、单个标签格式与冲突处理说明，需要明确喜欢与不喜欢同时包含同一标签时的规则。
- 资料更新模型不再显式声明 nullable；当前前端清空生日、性别、省市会提交 null。需要明确“保持原值”和“清空字段”的约定。作者编辑菜品则已经明确省略/null 保持原值，说明空串可清空，不能据此推断资料更新也采用相同语义。
- `ErrorResponse` 只有字符串 code，没有完整错误码与恢复动作表。账号冲突恢复还存在泛型 `Result_AnyResponse`，需要具体 challenge/reset 响应才能完整实现。
- 部分公开操作同时声明了 `SaToken` security 和“可选登录”的权限说明；接入时应按公开说明实现，并用游客实际请求确认部署行为。

## 管理端后续能力

新增目录冲突裁决、授权复核、资料授权复核、账号安全复核及密码冲突恢复接口，适合单独增加管理页，优先级低于前台主流程。

`/auth/password-conflict/challenge`、`/auth/password-conflict/reset` 受 `app.account.multiwriter.enabled=true` 控制；不能作为所有用户通用的“忘记密码”。无登录撤回授权也有配置开关，且“撤回授权”不是“注销账号”。应先确认测试环境是否启用，以及具体响应结构。

已有活动菜品/活动饭局接口不等于专题目录接口，不能直接用它们填充当前专题页。

## 这份文档仍未补齐的能力

评论与回复/评论点赞、举报、意见反馈、设备会话列表和远程下线、屏蔽名单、通知偏好、账号注销、换绑手机号完整流程、专题目录与详情、他人的菜品列表、足迹清空、真实地图选点与导航服务均未形成可直接替换当前占位或 Mock 的完整接口。

`SendCodeReqRequest.scene` 包含 `change/forget` 等枚举不代表换绑或匿名找回的后续接口已经具备；同理，推荐偏好接口不代表通知偏好已具备。

## 接入前建议与后续实施

建议先迁移类型、错误处理和权限，再完成“全站查询与收藏筛选 → 推荐校区饭点 → 发布返回 ID、初始标签与云端展示 → 作者编辑删除 → 手机登录与设置密码 → 统一认证与口味偏好”，管理复核单独安排。
