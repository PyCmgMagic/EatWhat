# 前端搭建与功能实现：接口问题清单（v2）

日期：2026-10-21。唯一依据：`吃什么接口文档v2-openapi.yaml`，版本 `auth-renewal-20261019`。

本清单用于前后端对齐和排期，聚焦哪些页面无法完整实现、哪些联调规则需要补充。已核对 v2 路径、参数、角色和模型；未调用部署服务。下文的“缺失”仅表示当前契约未定义，不能据此认定后端源码没有实现。

基础页面与已有接口的封装可以开始。完整的发现、发布和分类整理体验，需要先处理以下问题。

## 一、优先级与问题类型

- **P0：核心流程联调前解决。** 需要修改接口或给出可执行约定。
- **P1：首版承诺相应功能前解决。** 可通过明确缩小首版范围暂缓。
- **P2：后续扩展。** 只有确定要做相应功能时才补充。
- **明确缺口**：当前接口参数、返回值或角色不足以直接完成目标行为。
- **约定不足**：已有相关接口，需要补充状态、规则或真实样例。
- **产品决策**：接口规则明确，需要确认是否符合预期；不直接算接口错误。

### F01：创建接口不返回 ID，是最直接的发布断点

证据：`POST /restaurant/add`、`POST /foods/upload` 返回 `Result_VoidResponse`，data 只能是 null；`CreateFoodDTORequest.restaurantId` 必填；标签操作依赖菜品路径 id。

阻断的连续操作：

1. 用户新建餐厅 → 拿到 restaurantId → 在该店发布菜品。
2. 用户提交菜品 → 拿到 foodId → 添加标签 → 打开准确的详情页。

建议创建返回 `{ id }` 或完整资源。Activity 和 Hub 的创建也返回 Void，如果发布/新建后需要直接跳详情，同样应返回 ID。

前端可以在成功后返回列表，但不能据此实现准确的自动关联。不得靠“同名搜索”或“我的列表第一项”猜测新 ID。

### F02 / F03：筛选需要由后端对完整候选集合执行

当前只能在某餐厅内按系统/个人标签筛选。收藏列表不接收标签条件，全局菜品列表也没有查询入口。

例如“全部收藏中标了想吃的菜”与“所有餐厅的 20 元内主食”，当前都没有完整查询接口。前端仅过滤当前页会漏掉其他页；拉取所有页再筛选只能作为小规模临时方案，不应作为正式分页和搜索能力。

建议定义：可组合筛选项、同类标签 AND/OR、排序及次级排序、分页上限、空结果行为。不要只增加 UI 上的分类按钮，而不给它对应的后端查询含义。

### F04 / F05：现有接口不能通过前端绕过权限

F04 中“作者可以管理自己发布的内容”并非当前已定义能力。不能仅在前端比较 accountId 就调用 admin 接口；需要后端提供对应权限与归属验证。若首版由管理员维护，应明确隐藏或解释作者侧的编辑/撤回入口。

F05 中手动选 Hub 后，可以讨论用其中心坐标搜索，这符合 search 的参数形状。但仍需确认坐标非空、radius 单位和覆盖范围；界面要表达“所选区域”，不能称作用户真实位置。也可以增加无需设备定位的普通目录接口。

## 三、已有接口但联调约定不足的问题

| 编号 | 优先级 | 问题 | 前端受到的影响 | 后端需交付 |
| --- | --- | --- | --- | --- |
| C01 | P0 | 登录/授权结果缺少完整状态表和样例 | 容易把 proof、注册受理或身份同步中误判为已登录；续期后恢复路径不明确 | 成功 token、20005/20006、临时 proof、授权过期/撤回/未就绪的真实响应及下一步 |
| C02 | P0 | 图片上传后如何读取展示未明确 | 上传和业务保存可完成，但图片 src、鉴权、有效期与刷新无法可靠确定 | 明确读接口返回 key 还是 URL；key 如何解析；如使用签名 URL，给出获取与续期协议 |
| C03 | P0 | 业务接口和文件存储的浏览器联调配置未给齐 | API 请求、自定义头、文件 PUT 和认证跳转需要实际验证 | 可用 baseURL、前端 Origin/CORS 约定、satoken 头、对象存储 PUT 配置、校内认证完整跳转方案 |
| C04 | P1 | 标签匹配、删除与重名规则未定义 | 多选筛选、改名冲突、撤销公共标记和删除个人分类容易各端理解不同 | AND/OR、数组写法、幂等、计数含义、重名/删除影响和个人可见范围 |
| C05 | P1，若首版展示 | 通知 type/targetType 无枚举，data 是字符串 | 点击通知无法可靠选择路由或解析附加信息 | 事件及资源类型表、payload 样例、资源已删除/无权限时行为 |
| C06 | P1 | 可空、时间、编辑清空与分页规则宽松 | 客户端类型只能大量可选；日期、清空字段和翻页行为易不一致 | 关键响应字段保证、时间单位、null/省略/空数组语义、分页及排序规则 |

### C01：需要的是可执行的状态协议

`AuthReply.data` 可以是 SaTokenInfo、ConsentView、临时 consentProof 对象或 null。政策与同意接口受 `app.account.enabled=true` 控制；无 proof 的 grant 需要已登录校内权威站会话，不能按“任意匿名提交政策版本”使用。

需要后端逐一给出：业务 code 与 data 形态、是否保存会话、应展示的状态、是否需要用户操作、何时重试登录、哪些状态可有限轮询。尤其要区分授权同意、identityReady、registrationAccepted、verified 和真正取得 token。

`status/backfillStatus/cleanupStatus` 没有枚举，20005/20006 没有完整的逐项映射；AuthReply 的 proof 分支又没有必填判别字段。建议补稳定分支标识与必要字段，不让前端靠 msg 文案猜流程。

### C02：文件写入流程明确，展示规则仍需明确

v2 已规定：预签名 → 向 putUrl PUT 原始文件 → `/upload/complete` → 将 key 写入业务字段。这部分应按文档实现。

剩余问题是“读”：Food.pictureUrl、Restaurant.pictureUrl、avatar 的字符串究竟是什么，以及如何转成能访问的展示地址。若是公开 URL 可直接用；若是 key，应给确定的解析规则或读取接口；若是临时签名 URL，应给刷新方法。

还需确认 MIME 白名单、单文件上限、PUT 签名头、expireAt 单位、批量文件对应关系和 complete 的重试语义。文件上传使用独立请求实例，避免向对象存储发送本站会话头。

### C03：是待核验配置，不是已证实的服务故障

目前未测试服务可访问性、CORS 或存储配置，不能断言这些配置已经有错。这里只列出浏览器联调必需的信息。

已明确且前端可直接遵守的两点：

```http
satoken: Bearer <tokenValue>
```

请求头名称以登录返回 tokenName 为准。网关使用 `/api` 加原始路径，省市接口为 `/api/api/location/...`，不能自动去重。

### C04：个人分类管理还有一个按需求补充的入口

目前可以通过给菜品添加 names 来创建或关联个人标签，但 `/foods/tags/my` 只有查询，另有改名/删除，缺少独立创建空标签的接口。

如果界面允许用户先建“想吃”等分类再加入菜品，需要补创建接口。如果选择“整理某道菜时才新建分类”，可以沿用现有添加方式。

### C06：首版至少固定这些字段规则

- 成功响应中资源 id、列表 items、分页状态是否保证存在；点赞状态为 null 是未知还是未点赞。
- 创建/更新时间和签名过期时间的单位；ConsentView.validUntil 当前支持 ISO 或毫秒，不应全部按同一数值格式解析。
- 编辑时省略字段、null、空串、空数组是否保留或清空。
- page/pageSize/limit/radius 的上下界、默认值、排序及重复互动幂等结果。
- 数值 ID 的实际范围与前端表示；UUID 文件标识不能和菜品数值 ID 混用。

## 四、必须先定下来的产品权限规则

这些规则已经写在 v2 中，不应直接报成接口缺陷；但它们决定页面能否向目标用户开放。

1. **核心菜品浏览与整理要求 verified。** 若预期游客或仅登录用户可看菜，需要后端调整读取策略；否则前端应安排清晰的认证引导。还需明确哪些认证方式授予 verified。
2. **搜索餐厅不要求额外角色，餐厅详情要求 verified。** 若保留该策略，搜索结果点击后应有认证提示。
3. **普通菜品/餐厅由管理员编辑删除。** 若是用户自主分享平台，需确定作者纠错/撤回方案；不能默认作者已有权限。
4. **同意、目录同步与资料同步接口依赖开关。** 前端需按部署启用对应能力，404 不能一律解释为登录过期或用户没权限。
5. **Food 是菜品条目还是独立分享，需要统一理解。** 当前必须绑定餐厅；若要分享自制餐等不依赖餐厅的内容，需明确使用专题动态还是补通用分享模型。

## 五、按首版范围决定是否增加的功能

| 功能 | 当前情况 | 建议 |
| --- | --- | --- |
| 评论、回复、评分 | 未定义对应接口 | 若首版要做评论区或星级评分，需成套设计；否则不展示可操作入口 |
| 关注用户内容流 | 有关注关系，无关注内容流 | 有“关注”Tab 才需要补作者关系过滤的内容查询 |
| 公开美食清单/可分享收藏夹 | 有个人标签，无清单实体和公开性/顺序等约定 | 个人整理可先用标签；要公开分享清单再补模型与权限 |
| 举报及处理状态 | 未定义举报/审核流程 | 面向真实用户开放分享前，明确反馈和管理员处理方式 |
| 营业状态、营业时间、距离 | 当前 Restaurant 未提供这些展示字段 | 若页面要展示，需补数据来源和字段；不能用设计稿占位值冒充真实结果 |
| 浏览历史清空/删除 | 只有查询，记录机制也未说明 | 需要管理历史功能时补操作与记录规则 |

这些属于范围选择，不应全部列为“开始写前端前必须完成”。

## 六、建议发给后端的首批任务

1. **F01：创建返回 ID。** 至少覆盖 restaurant/add 和 foods/upload；讨论初始标签一并保存。
2. **C01/C03：补登录、授权、认证和浏览器联调样例。** 让前端能准确管理会话与角色。
3. **C02：明确图片读取协议。** 提供一个完整的上传、保存、读取展示样例。
4. **F02/F03：补跨餐厅菜品查询与收藏标签筛选。** 这两项直接对应发现和分类整理。
5. **F04/F05：确定作者管理与无设备定位浏览方案。** 按确定后的首版流程改接口或调整界面范围。
6. 首版涉及他人主页、年夜饭点赞或忘记密码时，再同步补 F06/F07/F08。

验收关注完整用户行为：新店到菜品发布不中断、跨页收藏筛选不漏项、作者管理权限正确、登录不把 proof 当 token、图片发布后能显示、拒绝定位仍有明确路径。

本清单没有修改原始 YAML，也没有把缺少运行验证的行为当作已确认故障。
