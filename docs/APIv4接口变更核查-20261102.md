## 影响现有前端的重点变化

### 1. 发布校验收紧，文字长度按 Unicode code point

`CreateFoodDTORequest` 的规则：

- 菜名 strip 首尾空白后为 1–12 个 Unicode code point。
- 说明为 0–300 个 Unicode code point。
- 价格为 0–999，最多一位有效小数，`multipleOf=0.1`；`1.00` 等数值等价形式可以接受。
- 初始个人标签规范化空白后为 1–10 个 Unicode code point，各类标签最多 20 项。
- 菜品图片为 1–9 张，必须是 `foods/` 存储 key，不接受签名 URL。
- DTO 总说明另明确新发布的价格、分类、至少一个饭点、舞台色、两个备色及裁切信息要求；不能只依据 JSON Schema 的 `required` 三项来判断全部业务必填项。

当前 `frontend/src/desktop/DesktopPublish.tsx` 仍允许菜名 64、说明 2000、价格 999999.99、步长 0.01；`frontend/src/mobile/bridge.tsx` 的提交校验仍允许旧价格范围与两位小数，需要同步适配。

### 2. 编辑规则保留历史值

`EditFoodDTORequest` 和 `EditRestaurantDTORequest` 明确使用条件校验：省略/null 保持原值，变化后的字段按新规则校验；未变化的历史超限值可以保留。说明空串可清空。

不能把新发布规则无条件套到整个编辑表单，否则用户只改一个字段时可能无法保存历史菜名、价格或说明。旧非 `foods/` 图片引用可通过省略字段保留；替换时必须提交有效 key。

新建餐厅的名称为 1–20、地址为 1–30 个 Unicode code point，门头图片最多 1 张且为 `restaurants/` key。修改餐厅时，未变化的历史多图数组可以保留，不应自动删图。

### 3. 创建、编辑结果增加审核受理信息

`CreatedResourceVOResponse` 增加必返但可空的 `moderationStatus`、`revisionId`。原生审核路径可返回 `PENDING` 和私有修订 UUID，其他创建路径为 null。

`PUT /foods/my/{id}`、`PUT /foods/edit/{id}` 的成功 data 在启用原生审核时可以是修订受理结果，未启用时为 null。`PUT /restaurant/edit/{id}` 改用 `RestaurantEditReply`，也允许返回审核受理对象或 null。

当前 `frontend/src/api/service.ts` 的创建助手只保留 `{id}`，编辑调用按 void 消费；发布页随后直接进入详情。适配时应保留审核状态和修订 ID，并区分受理、待审核与已公开结果。审核查询的新路由目前仍属于文档标记的未上线接口。

### 4. 资料冲突裁决改用候选 head ID

两个资料冲突 POST 的请求模型从旧共享 `ResolveRequestRequest` 改为 `ProfileConflictControllerResolveRequestRequest`，包含必需 `expectedRevision` 及可选 UUID `selectedHeadId`。读取模型明确 `heads[].id` 就是该候选编号。

这给上一轮读写不一致的问题提供了对应关系。当前 `service.ts` 的两个资料冲突方法仍使用旧共享 DTO，`sync-management.ts` 另有目录冲突依赖该旧模型；应按具体控制器拆分，不能全局替换或直接开放旧裁决表单。

### 5. 餐厅目录及详情扩展

`/restaurant/browse`、`/restaurant/search` 增加校区、多分类、价位、推荐、收藏、排序等筛选；search 的经纬度改为参数层面的可选项。模型新增封面、距离、均价/价位、代表菜品、口味汇总、评分、个人收藏和营业状态等字段。

状态字段包括 `READY`、`SYNC_PENDING`、`NOT_LOGGED_IN` 等；同步未就绪与真实为空需要分别展示。菜品模型也增加可空 `distanceMeters`。

### 6. 登录与上传类型调整

- 登录、注册、首次设置登录名和查重增加 `username` 别名，保留 `userName`；当前前端继续提交 `userName` 的方式仍有契约依据。
- `SaTokenInfoResponse.loginId` 与 `PhoneLoginDataResponse.loginId` 从 string 恢复为 `string | integer`。当前业务登录使用 token 字段，不依赖该值做数字计算；生成类型及上一轮的字符串类型断言需要同步调整。
- 上传 `biz` 新增 `comments`、`feedback`，原有 `foods` 等仍保留。
- 管理员封禁请求和用户资料增加 ISO 时间形式的 `banUntil`。

## 保持兼容及仍缺少的能力

- `GET /auth/consent` 仍为 `status`、`identityReady`、`policyVersion` 三字段；上一轮修复保持有效，不恢复“注册已接受”。授权和撤回进度仍独立。
- `GET /foods/recommend` 仍使用分页结果里的 `data.items`，没有改成裸数组；当前推荐解析方式保持匹配。
- 文档未列出评论列表、发布、回复、点赞或删除路由。`comments` 上传分类和 `CommentDetailResponse` 模型不代表具备评论 CRUD 接口。
- 文档约定日期/时间字段使用 ISO 8601；`createdAt` 等 Long 字段仍是 Unix 毫秒，应按具体字段模型处理。
